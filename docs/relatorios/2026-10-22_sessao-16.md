## Mudanças e decisão

- `createLocalGoogleIntegration` exige opt-in `GOOGLE_CALENDAR_CREDENTIAL_STORE=secret-service`. Omitir ID Calendar usa ID do login; omitir segredo Calendar usa segredo do login somente entre IDs iguais após trim. Override de ID diferente nunca recebe segredo do login; Desktop público aceita segredo ausente. Segredo Calendar explicitamente vazio impede fallback.
- Login configurado sozinho continua retornando `null`. Configuração Calendar parcial, segredo isolado, cofre inválido ou ID explícito vazio falha sem imprimir valores. Foram preservados consentimento próprio, PKCE, `include_granted_scopes=false` e refresh Calendar separado no Secret Service backend.
- Testes novos verificam configuração, URL de autorização para os dois modos e formulários de troca/refresh com fetch falso, sem acessar cofre. O teste existente de escopo insuficiente agora também comprova zero chamadas a `CredentialStore.put`.
- README, contrato Calendar, arquitetura JSON e [decisão](../decisoes/2026-10-22_calendar-oauth-client-reuse.md) descrevem cliente/sessão/consentimento/tokens e habilitação Calendar API no mesmo projeto. Corrigida a afirmação de que logout não revoga Calendar: o código de logout tenta revogar seu token, e o Google documenta revogação por projeto, inclusive outros clientes. Desconectar ou recusar escopos também pode exigir novo login e conexão Calendar. Nenhum token foi migrado; escopos de tokens históricos não foram inferidos.
